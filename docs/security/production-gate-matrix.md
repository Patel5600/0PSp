## Status rule

Every **pre-launch** gate below has a binary production status. The external-audit row is separately marked **DEFERRED** and is explicitly not a pre-launch acceptance criterion. **GO** means the exact gate described has adequate implementation and evidence for its limited scope. It does not automatically approve the complete protocol. **NO-GO** means the release criterion is not met; a green unit-test job, user risk acceptance, or an external-audit deferral cannot substitute for missing security behavior.

## Immediate next sequence

1. **Keep protocol versions separate.** RFC-02 is normative for V2 only. The CHp4.7 identity/nullifier design is isolated in `docs/theory/spend-relation-v3-candidate.md` as non-normative research material. Do not change frozen V1/V2 formulas or KATs, and do not accept candidate V3 objects as production spends.
2. **Establish a viable proof backend first.** Run the pinned OpenVM v2 STARK path and the Aurora/libiop spike as separate candidates. For OpenVM, generate/verify an actual 0PSP fixture proof and establish whether the selected parameters can substantiate the current 128-bit PQ target and witness hiding; do not count guest compilation as proof evidence. For Aurora/libiop, build an actual SHAKE256-384 relation in its claimed ZK mode, review masking/degree/transcript assumptions, calculate QROM security, and measure execution. If neither survives, stop the V3 HMAC cost experiment and revisit the design rather than extrapolating from static row models.
3. **Measure the actual V3 relation before choosing a PRF.** On a backend that passed Step 2, benchmark CommitV3, NullifierV3/HMAC-SHA3-384, key-commitment opening, anchored output derivation and the selected authorization predicate. Record pinned commit/dependencies, security assumptions, constraints/trace rows, prover and verifier time, peak memory and serialized proof size. Compare alternatives at equivalent stated security levels; do not assume KMAC is cheaper because it uses Keccak.
4. **Close the authorization specification gap.** Evaluate ML-DSA-87 threshold signing as the leading experiment, not an approved scheme. Reconcile the exact-release audit-warning conflict and GPL-3.0 package scope; pin source/dependencies; freeze only a reviewed canonical key codec, message/context, key-generation/DKG model and corruption threshold. Bind the signature verifier to the exact hidden authorization key in BundleV3 and canonical transaction digest inside the complete relation. Do not classify a signature helper or PR #31's NOAUTH guest as production authorization.
5. **Prove one complete shared-witness relation.** Bind the exact commitment opening and value, recipient bundle/authentication/key-commitment opening, same-witness nullifier, output identities derived from one-use anchors plus canonical global slots, complete canonical transaction/output list, authenticated root/state head, value conservation/range/overflow rules and the selected authorization predicate. Mark every predicate as proof-enforced or atomically ledger-enforced.
6. **Compose and test state transitions.** Join authenticated finalized deposit/custody verification -> trusted DepositAuthorization -> proof verifier -> durable atomic ledger; exercise replay, duplicate commitments/nullifiers, races, crash, reorg and recovery. Remove injectable test callbacks from the production composition.
7. **Release remains NO-GO** until all mandatory gates have evidence on one exact release SHA, adversarial checks pass, and an internal threat-model audit closes P0/P1 findings. External audit remains explicitly NOT PERFORMED; no missing implementation or proof obligation is waived.
