# 0PSP Constructionable V0 — Namespace-Bound V2 Target

**Status:** V2 component implementation exists; end-to-end construction and security proof do not. Production remains **NO-GO**.

## Architecture decision

Retire the uninstantiated LoTRS selection proof + separate SHAKE STARK + bridge-commitment stack. V2 targets **one post-quantum zero-knowledge argument for the complete spend relation**. This is a construction target, not a claim that the relation is already implemented or that one backend is automatically suitable.

V2 explicitly binds every spend to a namespace comprising the ledger/network instance, deployed protocol instance and asset. The older V1 nullifier and commitment helpers remain for historical tests only. V1 and V2 must never be mixed in a spend.

## Canonical namespace and coin identity

Each of ledger_id, deployment_id and asset_id is a 32-byte canonical identifier produced by a chain-specific adapter. Display names, tickers and ambiguous string encodings are forbidden. V2 derives:

    namespace_id = SHAKE256-384(
      "0PSP-NAMESPACE-v2-SHAKE256" || 0x02 ||
      uint16_le(32) || ledger_id ||
      uint16_le(32) || deployment_id ||
      uint16_le(32) || asset_id)

The output is 48 bytes. The adapter must define canonical mappings that distinguish any ledger instances, deployments and assets that must not share spend scope.

A coin ID is a fresh opaque 32-byte identifier generated by the native OS-backed RNG. It is not a namespace-truncated hash. The full coin identity is (namespace_id, coin_id). A live mint ledger must atomically reject duplicates of that pair and register the commitment in the same state transition. The current in-memory MintRegistryModel tests only this logic locally; it is not a consensus ledger. Real chain adapters, reorg handling and durable atomic uniqueness remain open.

**Issuer-privacy blocker:** the party that creates or learns coin_id and r_nf can calculate the public nullifier later and link the spend to that issuance record. If anonymity is meant to include the mint authority, coin-ID/nullifier-secret creation and commitment issuance must be designed so the authority does not learn the opening, or the trust model must explicitly exclude issuer privacy. A blind-issuance protocol is not implemented. A ZK spend proof cannot erase an opening already known to the issuer.

## Commitment V2 candidate

The functional candidate is:

    C = SHAKE256-384(
      "0PSP-COIN-COMMIT-v2-SHAKE256" || 0x02 ||
      uint16_le(len(params_id)) || params_id ||
      uint32_le(len(pk)) || canonical_pk ||
      uint64_le(value) ||
      uint16_le(48) || namespace_id ||
      uint16_le(32) || coin_id ||
      uint16_le(36) || r_nf ||
      uint16_le(36) || rho_C)

The output is 48 bytes. The amount is an unsigned 64-bit little-endian value. The per-coin nullifier secret r_nf and commitment salt rho_C are independent 36-byte values. Public-key bytes must be canonical for the exact threshold-signature scheme. The parameter identifier is non-empty, versioned and length-prefixed.

The Python reference and native OpenSSL implementation use this same encoding; the native and Python known-answer vectors match. Helpers compute/recompute openings but do not implement a proof. If canonical encoding is injective over accepted openings, a binding break gives two distinct inputs to SHAKE256-384 with the same output, hence a hash collision. This is a conditional reduction. A 384-bit output has generic quantum collision-search scale around 2^128 oracle queries under the BHT-style idealized model, not 192-bit quantum collision security. The final public-key codec, accepted input domain and concrete query/security model still need to be frozen and reviewed.

Hiding is still open. The 288-bit salt is not, by itself, a hiding proof. The final argument must define a classical-RO or quantum-RO game, account for the visible nullifier and all other public outputs, and prove a query-dependent bound. A generic 2^144 quantum-search scale is only an idealized salt-search estimate and not a protocol hiding theorem.

## Nullifier V2 contract

For namespace_id (48 bytes), coin_id (32 bytes) and r_nf (36 bytes):

    nu = SHAKE256-384(
      "0PSP-NULLIFIER-v2-SHAKE256" || 0x02 ||
      uint16_le(48) || namespace_id ||
      uint16_le(32) || coin_id ||
      uint16_le(36) || r_nf)

The absorbed preimage is exactly 149 bytes and the output is 48 bytes. It is namespace-bound directly, not by a minting convention alone. The input crosses SHAKE256's 136-byte rate boundary, which must remain covered by vectors/tests. The same namespace, coin ID and secret must be bound in the commitment opening and the proof.

V2’s domain/version prefix prevents accidental byte-level reuse with V1; the ledger still must explicitly reject invalid versions and must never silently migrate an old nullifier state.

## Exact target spend relation

Public statement:

    x = (namespace_id, R_C, nu, M, state, params_id)

Witness:

    w = (j, C_j, pk_j, value, coin_id, r_nf, rho_C, sigma_th)

The one proof must establish all predicates for the same hidden selection index j:

1. Membership: j is in range and C_j = R_C[j].
2. Commitment opening: C_j is exactly the V2 commitment computed from the same public namespace, canonical key, value, coin ID, nullifier secret and salt.
3. Threshold authorization: Ringtail verifies sigma_th under that same key for transaction digest M.
4. Nullifier: nu is exactly the V2 nullifier for that same namespace, coin ID and nullifier secret.
5. Ledger/policy: the coin is eligible at the committed state, the state is current, the nullifier is unspent, and value-conservation/output/fee policies hold.
6. Privacy: the proof hides j, the opening and the threshold signature except for explicitly allowed leakage.

M must bind protocol version, namespace, nullifier, inputs, outputs, fees and the required ledger/network context. The ledger atomically rejects duplicate nullifiers and stale state. A relation that checks commitment opening against one key but signature validity against another key is incorrect.

The full relation must be specified in the selected proof system. It cannot be created merely by serializing the values or running the checks outside the proof.

## Threshold signature choice

Ringtail is the target two-round lattice threshold signature. Its paper reports LWE-based security, but the upstream Go repository labels itself an academic proof-of-concept that has not received careful code review and is not production-ready. Pin an immutable revision, license, parameters, canonical key/signature encoding and key-generation model. Use the [Ringtail adapter contract](ringtail-adapter-contract.md) as the integration gate. The existing design assumed dealer-based key generation; if that assumption is unacceptable, design and prove a DKG separately. Do not put the prototype networking demonstration inside the ledger runtime.

Even after ordinary Ringtail signing and verification tests pass, its verification predicate must be represented inside the one anonymous proof using the same hidden public key bound into the commitment. A standalone FFI adapter is not sufficient.

## Proof backend feasibility decision

Evaluate SmallWood first as an experimental candidate alongside a concrete lattice-proof approach. SmallWood is a hash-based zero-knowledge argument aimed at small-to-medium statements, and its paper discusses hash-preimage and lattice-based relations. Its reference implementation is explicitly a prototype and unaudited. This is a candidate for a feasibility experiment, not an approved backend.

The experiment must encode the **exact** V2 relation, including SHAKE commitment/nullifier, canonical key and range checks, Ringtail signature verification, and all membership/policy constraints. Report proof bytes, prover time, peak memory, verifier time, security parameters and exact build/configuration. Reject the backend if it only supports the hash relation or signature relation in isolation, provides no required post-quantum security property, or cannot keep every predicate bound to the same witness.

## Implementation phases

### V2-A — Component conformance (partially implemented)
- Canonical namespace format and fixed 48-byte V2 namespace ID.
- Native 32-byte coin-ID generation; V2 nullifier; reference and native known-answer vectors.
- V2 commitment encoding and fixed vector.
- Domain separation, namespace substitution, fixed-size/error checks and local mint-uniqueness model.
- CI compile of V2 timing screen without treating shared-CI timings as security evidence.

### V2-B — Real mint/ledger adapter (OPEN)
- Define real chain/deployment/asset byte mappings.
- Implement durable atomic uniqueness for (namespace_id, coin_id).
- Define version migration, state roots, reorg/finality and duplicate-nullifier persistence.
- Verify that mint and spend use the exact same namespace bytes.

### V2-C — Commitment theorem (OPEN)
- Freeze canonical public-key and parameter encodings.
- Formalize the binding game and hash-collision reduction.
- Prove hiding in the selected classical/quantum random-oracle model, including nullifier visibility and all permitted outputs.
- State quantitative query bounds and concrete security levels.

### V2-D — Ringtail integration (OPEN)
- Pin and audit source, tests, parameters and license.
- Build deterministic vectors and negative tests for the adapter.
- Prove the signature-verification statement is expressed for the key bound by the coin commitment.

### V2-E — Single proof backend (OPEN)
- Encode every predicate in one ZK argument and test adversarial witness substitutions.
- Establish zero knowledge, knowledge soundness and post-quantum security for the exact instantiation.
- Record proof sizes, runtime and peak memory from a real build, not estimates.

### V2-F — Full security theorem and side channels (OPEN)
- Prove spend soundness, mint uniqueness, double-spend resistance, commitment binding/hiding, threshold authorization, anonymity/unlinkability and compositional post-quantum security.
- Define permitted leakage, including intentional same-coin nullifier linkability.
- Review source/data flows, release binaries, OpenSSL/provider internals, FFI and memory lifetime on every supported target.
- Run controlled timing/leakage tests on supported hardware; passing tests are evidence only for those builds/experiments.
- Obtain independent cryptographic review and resolve all release-blocking findings.

## Release decision

**NO-GO.** V2 namespace-bound component functions, known-answer tests and a local timing screen exist. No live mint ledger, completed commitment-hiding theorem, Ringtail integration, complete single proof, composed security reduction, independent audit, end-to-end benchmark or full-path side-channel assurance is claimed.
